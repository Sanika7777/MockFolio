# Changelog

## Task 1 — Central transaction layer with deadlock retry

- Added `backend/transactions.py`: `is_retryable()` (true only for MySQL 1213 deadlock / 1205 lock-wait-timeout on `OperationalError`), `run_in_transaction()` (fresh `SessionLocal()` per attempt, rollback + jittered exponential backoff on retryable errors, re-raise otherwise), and a thread-safe metrics counter (`attempts`, `retries`, `deadlocks`, `lock_timeouts`, `gave_up`) exposed via `get_metrics()` / `reset_metrics()`. Retries are logged at WARNING on `mockfolio.tx`.
- `backend/trading.py`: `execute_trade()` no longer commits or refreshes; it flushes so `order.id`/`trade.id` are populated and returns the trade for the caller/wrapper to commit. Added `execute_trade_tx()`, which runs `execute_trade` through `run_in_transaction`.
- Fixed the BUY-side gap-lock deadlock at its root: first-time buys no longer take a `SELECT ... FOR UPDATE` on a non-existent `holdings` row (which takes a gap lock at REPEATABLE READ and deadlocks two concurrent first-buys against each other). Replaced with a single `INSERT ... ON DUPLICATE KEY UPDATE` (`_upsert_buy_holding`) that lets MySQL resolve new-vs-existing atomically; the weighted-average math is computed in the `UPDATE` clause before `quantity` is overwritten. Lock order (stock → account → holding) is unchanged; SELL still locks the holding row directly since it must already exist.
- `backend/main.py`: `/trades/{side}` now calls `execute_trade_tx()` instead of managing its own session/commit for trades. `TradingError` still maps to 400 (never retried); a retryable error that exhausts all attempts maps to 503 `{"detail": "Market is busy, please retry"}`; anything else stays 500.
- Added `tests/test_transactions.py` (unit, no DB): `is_retryable` is True for 1213/1205 and False for `TradingError`, `IntegrityError`, and a generic `Exception`.

**Not yet verified in this environment:** the live 8×15-BUY/5-round concurrency run (0 orders lost, money invariant, `retries > 0`) requires real MySQL, which this WSL sandbox cannot currently reach (see conversation — host grant issue on the Windows-side MySQL server, host `172.23.146.97` still refused with error 1130 despite two grant attempts). Code is written and reviewed against the documented deadlock mechanism; the live proof is deferred until DB access is restored, and will also be formalized as `tests/concurrency/test_no_orders_lost_to_deadlock` in Task 6.

## Task 2 — Make idempotency safe under a race

- `backend/trading.py`: added `IdempotencyConflict` exception, `_is_duplicate_client_order_key()` (checks the MySQL 1062 duplicate-entry message names `client_order_key`, not some other unique index), and `_existing_trade_for_key()` — a shared lookup used both by the normal sequential-replay path inside `execute_trade()` and by the new race-recovery path, so both behave identically. It also now guards against key reuse: if the stored order's `user_id`/`stock_id`/`order_type`/`quantity` don't match the incoming request, it raises `IdempotencyConflict` instead of ever returning another request's (or user's) trade. This closes a latent leak in the old code, which returned the existing trade on a key match with no payload/user check at all.
- `execute_trade_tx()` now catches `IntegrityError` from the duplicate-key race (two simultaneous requests both pass the pre-check and race to insert the `Order` row), and — only when it's specifically the `client_order_key` unique index — resolves it in a **fresh session** via `_existing_trade_for_key()`, returning the winning trade to every caller instead of surfacing a raw 500. `IntegrityError` is not in `is_retryable()`'s scope, so this path is never retried by `run_in_transaction`, per the requirement.
- `backend/main.py`: `/trades/{side}` now maps `IdempotencyConflict` → 409 `{"detail": "Idempotency key reused with different request"}`.
- Added `tests/test_idempotency.py` (unit, no DB): duplicate-key message parsing, and `_existing_trade_for_key()`'s branching (matching replay returns the trade; mismatched quantity/side/stock/user all raise `IdempotencyConflict` and never return the trade).

**Not yet verified in this environment (same MySQL-access blocker as Task 1):** the live race test (8 simultaneous identical requests → 1 `orders` row, 8 identical successful responses, 0 HTTP 500), the different-quantity → 409 test, and the different-user → no-leak test all need a real MySQL connection to exercise actual concurrent `INSERT` races and multi-row state. The branching logic they'd exercise is covered by `tests/test_idempotency.py` against fakes; the true end-to-end proof is deferred until DB access is restored / Task 6.

## Task 4 — Lock-order helpers in one file + savepoints

- Added `backend/locks.py`: the only file in the codebase allowed to call `.with_for_update()` (`grep -rn "with_for_update" backend/` now matches only this file). `lock_stock`, `lock_account`, `lock_holding` each do one `SELECT ... FOR UPDATE`; `lock_stocks` locks a multi-stock set in ascending `id` order. Two env-driven switches for Task 7's demos: `MOCKFOLIO_LOCKING` (default on; `off` drops `FOR UPDATE` entirely) and `MOCKFOLIO_ORDERING` (default on; `off` skips the ascending-id sort). Both default to enabled so today's behaviour is unchanged unless a demo script explicitly flips them.
- Added `savepoint(db)` to `backend/transactions.py` — a thin context manager over `db.begin_nested()`.
- `backend/trading.py`: `execute_trade()` now calls `lock_stock`/`lock_account`/`lock_holding` instead of inline `with_for_update()`, with identical behaviour. Reordered so the `Order` row is created (and flushed) first, then the actual price/cash/holding/trade mutation runs inside `with savepoint(db):` — a failure in that block rolls back only that mutation before re-raising, leaving the order/lock work as it was at the moment of failure rather than a partial mix of old and new values.
- `backend/simulation.py`'s decay logic now calls `lock_stocks(db)` instead of its own inline `with_for_update()`.
- Added `tests/test_savepoint.py` — runs against a real (in-memory SQLite) engine, not a mock, so it's a genuine, currently-passing proof: a failure inside `savepoint()` reverts only the change made inside the block, a change made *before* the savepoint survives both the inner failure and the eventual outer commit, and a savepoint with no error commits normally. All 22 tests (14 previous + this task's) pass, including with `MOCKFOLIO_LOCKING=on` explicitly set.

## Task 7 — "Turn it off" demos for the report

- Added `scripts/concurrency_report.py`. Architecture note: `MOCKFOLIO_LOCKING`, `MOCKFOLIO_ORDERING`, and `TX_ISOLATION` are all read once at import time, so the script never mutates already-imported module state — instead it spawns one fresh subprocess per configuration, with `DATABASE_URL` overridden to `TEST_DATABASE_URL`'s value and the relevant switch set as an env var *before* that subprocess's Python starts. This means the app's real engine (isolation level, lock-wait timeout, connect-event listener) is exactly what's under test in every scenario, with no monkeypatching. Refuses to run if `TEST_DATABASE_URL` is unset or equals `DATABASE_URL`, same safety rule as Task 6.
- **Lost update demo**: one account, 10 concurrent BUYs, 5 runs at `MOCKFOLIO_LOCKING=off` and 5 at `on`. Real measured result: **locking=off discrepancies were `1401.51`/`2803.02`/`2803.02`/`2803.02`/`1401.51` (never zero); locking=on was `0.00` every single run.** Along the way, found (and confirmed is specific to the deliberately-broken `off` mode, not a production gap) that disabling locking can also throw a raw `OperationalError` ("SAVEPOINT ... does not exist") under heavy same-holding-row contention, not just silently lose cash updates — worth including in the report as a second, more dramatic consequence of turning locking off. Confirmed this can't happen with `MOCKFOLIO_LOCKING=on` (the default) because the account lock, taken before the savepoint in `execute_trade`, fully serializes any given user's trades, so two transactions can never be inside the holdings-upsert savepoint for the same holding at once.
- **Deadlock demo**: reuses the real `backend.locks.lock_stock` helper and `ORDERING_ENABLED` flag directly (no new locking code) in a script-level "buy two stocks" sequence that two threads run in opposite order. Real measured result: **`ordering=off` produced exactly 1 deadlock in all 3 runs (3 total); `ordering=on` produced 0 in all 3.** The `SHOW ENGINE INNODB STATUS` deadlock section was captured to `reports/deadlock_capture.txt` on the first deadlock detected — confirmed it contains a genuine `LATEST DETECTED DEADLOCK` section with both transactions' `WAITING FOR THIS LOCK TO BE GRANTED` entries and the `WE ROLL BACK TRANSACTION` victim line. This needed one more grant beyond Tasks 1-6's: `GRANT PROCESS ON *.* TO 'mockfolio'@'<host>'` (required for `SHOW ENGINE INNODB STATUS`).
- **Isolation comparison**: same mixed BUY/SELL workload (8 users × 10 orders), 5 runs each at `READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE`, DB reset between every run. Real measured throughput/latency (MySQL 8.0.39): READ COMMITTED ~76-111 orders/sec (314-385ms mean latency), REPEATABLE READ ~69-112 orders/sec (325-558ms), SERIALIZABLE ~34-97 orders/sec (359-1165ms) — SERIALIZABLE was consistently the slowest with the highest latency, matching the written explanation included in the report (`isolation_explanation` field / printed table) about why each level differs. 0 deadlocks and 0 retries across all 15 isolation runs at this workload size.
- Both required files produced: `reports/concurrency_results.json` (full per-run data, `generated_at`, `mysql_version`, `isolation_explanation`) and `reports/deadlock_capture.txt`. Ran unattended end-to-end via `python scripts/concurrency_report.py`. Full `pytest` (38 tests) still passes afterward.
